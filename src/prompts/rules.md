## Test generation rules

These rules are mandatory. The cheap-to-check ones are also enforced in code: a file that breaks them is rejected when you try to save it, and you get the reasons back.

### Locators
1. Priority order: `getByRole` with an accessible name, `getByLabel`, `getByPlaceholder`, `getByText` (use `{ exact: true }` where possible), `getByTestId` (this project's test id attribute is `{{testIdAttribute}}`), then CSS as a last resort.
2. Never XPath. Never auto-generated class names (`.css-1x2y3z`, `.sc-abcdef`) or DOM-position selectors (`:nth-child`, `div > div > span`).
3. Every locator is verified live to match exactly one visible element before you write it. Use the code from the "Ran Playwright code" section of the browser tool you just ran, or `browser_generate_locator` for the element. Never type a locator from memory or guess one.
4. Use `.nth()`, `.first()` or `.last()` only when the plan intends position (for example "the first product in the list") and say so in a comment on the same line or the line above.
5. Scope locators inside a container when names repeat: `page.getByRole("listitem").filter({ hasText: "Backpack" }).getByRole("button", { name: "Add to cart" })`.

### Assertions
1. Web-first assertions only: `toBeVisible`, `toHaveText`, `toContainText`, `toHaveURL`, `toHaveCount`, `toHaveValue`, `toBeEnabled`. Never `expect(await locator.textContent()).toBe(...)`.
2. Every meaningful action is followed by at least one assertion on its outcome: a URL change, a count change, new text, a confirmation message, or a changed value. Never assert only that a click succeeded.
3. Prefer assertions about relationships over hardcoded volatile values: assert the cart badge increased by one and the cart total equals the sum of its line items, not a specific price. Reading a value before an action to compare after it is fine (`const before = Number((await badge.textContent()) ?? "0")`).
4. Before writing an assertion, confirm it holds at that point in the live app with a `browser_verify_*` tool (`browser_verify_element_visible`, `browser_verify_text_visible`, `browser_verify_list_visible`, `browser_verify_value`).
5. No `waitForTimeout`, no `setTimeout`, no manual sleeps, no `networkidle`. Wait on locators or URLs through web-first assertions.

### Structure
- One `test.describe` per flow, one `test` per plan scenario, and one `test.step` per plan step, titled with the plan's step wording.
- Tags go in the describe title: `@dominion`, `@flow:<flow slug>`, `@role:<role>`, plus `@destructive` on a test that performs an irreversible action.
- Tests are independent: each test sets up its own state (navigates to its start page, adds its own items) and never relies on another test's leftovers. Tests may run in any order and in parallel.
- Tests start from the role's saved session and the project's baseURL: navigate with relative paths (`await page.goto("/products")`), never log in inside a test, and never hardcode credentials.
- Page objects (when enabled) only for pages used by two or more flows: one class per page under the page objects folder, locators as `readonly` properties, actions as methods, no assertions inside page objects. Reuse an existing page object method whenever one covers a step instead of writing a duplicate.
- Each spec file starts with the exact header comment you are given (generated by DOMinion, source plan path, run ID).
